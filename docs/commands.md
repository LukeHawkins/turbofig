# Commands

| Command | Does |
|---|---|
| `turbofig` | Installs/refreshes `turbofig.app`, starts the daemon, opens the app, and prints a 2-line pointer at the tray icon. On any other OS, or if the app could not be opened, prints the 3 connect steps on first run, or a 3-line status on a later run, instead |
| `turbofig js [--file <fileKey>] [--shot] [--dir <folder>]` / `turbofig js --guide [--dir <folder>]` | Reads JS code from stdin (or a full job JSON with an `op` field), sends it through the file bridge, waits for the result and prints the result JSON. `--shot` also screenshots the first node id the code returned (800 px longest edge by default; `--shot=N` sets the longest edge to N px, 1 to 16384, a bad value is exit 2) and prints that result as a second line. `--dir` names the bridge folder (it wins over `TURBOFIG_BRIDGE_DIR`; a relative path is made absolute). `--guide` reads no stdin: it starts the daemon if none runs, then prints the agent guide (version, binary, bridge folder, and the connected files with their keys, read from the daemon's registry with no plugin round trip) and exits 0, also with 0 files. Starts the daemon first if none runs. Exit 0: a result printed, even `"ok":false`. With `--shot` the exit code reflects line 1 only. Exit 1: no result, with one JSON line on stdout: `not_started` (the job never ran: resend), `started_unknown` (the daemon claimed it and it may have run: check before resending), or `bridge_error` (the folder is unusable, or the job could not be written or the result read, or `TURBOFIG_BRIDGE_DIR` is empty, or an older daemon that never claims jobs does not serve the folder: the job is removed after about 3 s and the error says `no turbofig daemon serves <folder>`). Exit 2: usage error, message on stderr (also: no input on stdin within 10 s). With `--shot`, a failed screenshot (line 2) is one `{"ok":false,"code":"shot_failed","reason":...}` line on exit 0: the code already ran, so never resend it. `reason` is `not_started`, `started_unknown`, `no_node_id`, `bridge_error`, or the plugin's own error code. `detail` is the cause (`timeout` or `daemon_stopped` for `not_started` and `started_unknown`, never resend wording; the error text for the other reasons). `retryAfterMs` (busy) and `outbox` (started_unknown) are copied through |
| `turbofig mcp` | Optional: runs a stdio MCP server for an MCP client (the file bridge, `turbofig js`, is recommended). Starts the daemon first if it is not already running |
| `turbofig start` | Starts the daemon detached in the background, if it is not already running |
| `turbofig stop` | Stops the running daemon |
| `turbofig status` | Queries the running daemon's `/health` endpoint and prints a readable report |
| `turbofig serve` | Runs the daemon in the foreground. For development, or for an autostart launchd service |
| `turbofig autostart on [--headless]\|off` | Turns on or off the launchd service that starts the app (or, with `--headless`, just the daemon) at login |
| `turbofig uninstall [--purge]` | Quits a running app, stops the daemon, turns off autostart, and removes the app bundle and its plist(s). With `--purge`, also removes the turbofig home folder's own files (the token, the plugin files, the inbox, the outbox, the log), and removes the folder itself only if it is then empty |

See [configuration.md](configuration.md) for the environment variables
these commands read.
