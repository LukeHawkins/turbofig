# Decisions

1. **Eval-first, ~4 tools (turbofig_execute / turbofig_get_selection / turbofig_screenshot / turbofig_status).**
   Why: fewer tool definitions for the agent to load, resilience (new Figma APIs work same-day), full capability through one tool. Baseline competitor figma-console-mcp already has eval + multi-file; turbofig differs on DX, a Rust single binary, and true always-on.

2. **Rust daemon via rmcp 3.1.0 (transport-streamable-http-server) + legacy_session_mode.**
   Why: client uses 2025-03-26 spec with mcp-session-id; rmcp defaults to the session-less 2026-07-28 spec. `legacy_session_mode: true` on `StreamableHttpServerConfig` with `LocalSessionManager` makes rmcp issue the `mcp-session-id` header on `initialize` and require it on subsequent calls.
   Phase 1 result: CONFIRMED. `initialize` returns `mcp-session-id`; subsequent calls reuse it; responses are SSE `data:` lines. A Rust integration test (`daemon/tests/transport.rs`) and a curl script (`scripts/handshake.sh`) both pass. The rmcp #1108 risk is retired.
   Fallback (retained, not needed now): if a future rmcp release breaks `legacy_session_mode`, hand-roll the transport with axum. Add a POST `/mcp` handler that assigns an `mcp-session-id` on `initialize`, stores session state in an in-memory map, and streams SSE `data:` responses. The WebSocket connection to the plugin stays on axum regardless. This is a drop-in replacement because the daemon already owns the axum `Router`.

3. **Ports are a product contract: default HTTP 18846, WS 18847, env-overridable (TURBOFIG_MCP_PORT / TURBOFIG_WS_PORT).**
   Why: obscure ports below 32768 avoid conflicts. The OS auto-assigns ephemeral ports at or above 32768 (Linux default 32768-60999, macOS 49152+), so a fixed server port there can collide. 18846 and 18847 sit below that floor, so the OS never auto-assigns them, and they are uncommon dev ports. A user with a conflict overrides both with one env var. This supersedes the earlier 3846/3847 choice; curl skills that targeted 3846 must update to 18846 (see Phase 11).

4. **eval blocks a Figma Community store listing; ship as dev-install.**
   Why: review rejects arbitrary server-run code. Keep the plugin hybrid-ready: a {type} dispatch table so a community-safe command vocabulary build is additive later with no rework.

5. **Distribution: primary `npx turbofig` using per-platform binary packages as optionalDependencies (the esbuild/Biome pattern).**
   Why: no postinstall network fetch, works on locked-down corporate networks. Secondary: cargo install, Homebrew tap, GitHub Release binaries + curl|sh. Daemon nudges on a newer version; plugin warns on version mismatch.

6. **SUPERSEDED by #29 (2026-10-04). Trainability: ship a generic good-designer taste baseline; user brand/project packs load on top and switch at runtime.**
   Why: the public build ships only the generic baseline, never private packs.

7. **Token strategy: subagent context firewall (screenshots live in disposable subagents), downscaled + milestone-only screenshots, shaped ids-first returns, batched execute.**
   Why: the whole product pitch is token economy. Every design decision is judged on token cost.

8. **Multi-file: true routing by fileKey (N independent sessions <-> N files), stronger than console-mcp's broadcast execute_across_files.**
   Why: per-session isolation is a hard requirement for concurrent multi-file design work.
   Phase 4 result: DELIVERED. The daemon holds a `conn_id`-keyed connection registry (one WebSocket per open file) and a `mcp-session-id` -> `fileKey` pairing map. `resolve_route(session_id, file_key)` in `daemon/src/lib.rs` picks the target by explicit `fileKey`, then the session pairing, then the sole named connection, and returns a clear no-plugin, ambiguous, or not-found error. A socket close cancels only that connection's pending requests, so files stay isolated. Two non-obvious mechanism facts: (a) a tool reads the session id via `Extension<http::request::Parts>` (rmcp 3.1.0 injects the HTTP parts into the request context; needs the `http` crate) and reads the `mcp-session-id` header; (b) an empty `mcp-session-id` header or an empty `fileKey` argument is normalized to no-target, so an empty string never records a bogus shared pairing and never forces a spurious not-found. Each of the 4 tools gained an optional `fileKey` argument; the tool surface stays at 4.

9. **Ship gate placement: Phase 5 is a provisional baseline only. The binding "far better than console-mcp" gate runs after Phase 7.**
   Why: the token and speed wins come from the helper library, the design-worker orchestration, and the subagent firewall added in Phases 6 and 7. Gating at Phase 5 would measure the system without its main levers.

10. **Context firewall is enforced, not just convention. Inline screenshots need an explicit opt-in and warn past a budget. File-mode plus subagent-read is the default path. Large reads without depth or fields are capped or warned.**
    Why: for a redistributed product the token promise cannot depend on client prompt discipline alone.
    Built in Phase 5: the "cap or warn" choice is an advisory `warning` field, never truncation. A read over `READ_BUDGET_BYTES` (20000) or an inline screenshot over `INLINE_SCREENSHOT_BUDGET_BYTES` (100000) gains a `warning` that names the remedy; the daemon never drops data, because truncating an `execute` result could corrupt it. Screenshots downscale to a longest-edge cap (`maxDim`, default 1200, floored at 1) via the `image` crate, and default to file mode; `fullRes` plus `return:"inline"` is the only high-res path. Read shaping is additive: `get_selection` keeps its seven-field base shape and adds opt-in `fields` and `depth` (capped at 5; `children` is reserved for the depth mechanism).

11. **SUPERSEDED by #29 (2026-10-04). Brand packs bind per session, keyed like the routing registry.**
    Why: concurrent multi-file sessions may need different brands at once, so a single global active pack would break isolation.

12. **Daemon lifecycle: launchd KeepAlive restarts the daemon on crash. Every call has a daemon-side timeout so a silent plugin never hangs a request. On restart the in-memory session registry is lost, so clients get a clear reinitialize signal rather than a silent error.**
    Why: always-on reliability requires automatic restart and clean failure signalling.

13. **eval security for redistribution: the daemon binds to 127.0.0.1 only. eval has resource guards beyond the timeout (runaway loop and memory). The prompt-injection and file-exfiltration risk is documented, because arbitrary eval on a user's open file is powerful. Acceptable for local use, called out for redistributed use.**
    Why: local-only binding limits the attack surface; documented risk keeps redistributors informed.
    DNS-rebinding defence (Phase 1, deliberate; pinned explicitly rather than left to the crate default as of the 2026-10-04 pre-release audit): `build_router` sets `StreamableHttpServerConfig.allowed_hosts` to `["localhost", "127.0.0.1", "::1"]` directly. This rejects a spoofed `Host` header with 403, so a browser page on a rebound domain cannot reach the loopback endpoint. We pin this rather than rely on `rmcp`'s current default (which happens to match) so a future crate upgrade that changes or widens that default cannot silently loosen this guard. We do NOT narrow it to `127.0.0.1:<port>` because curl skills may use `localhost`. `allowed_origins` stays empty (Origin validation skipped) because there is no browser client and the `Host` allow-list already blocks the browser attack path. Revisit `allowed_origins` if a browser client is ever added.

14. **Long-job durability: the daemon runs decoupled from any client session, so a session end or client crash never kills an in-flight job. Long design jobs checkpoint the plan spec and per-section progress to disk, and resume from the last completed section. Operations are idempotent, keyed by stable node id, so a resume never duplicates.**
    Why: the current supergateway stack dies with the session (SIGTERM), leaving big jobs half done. Decoupling plus checkpoint and resume lets a huge job survive a restart with completed work intact.

15. **File-bridge transport: the daemon services a watched folder (`~/.turbofig/inbox` -> `outbox`, env `TURBOFIG_BRIDGE_DIR`) so a client drives it with local file writes and reads only. Result files are written atomically (temp then rename).**
    Why: a locked-down Claude Enterprise policy forces a confirmation dialog on every curl and blocks self-adding an MCP server (tested 2026-08-05: `claude mcp add` returns "not allowed by enterprise policy"). The Write and Read tools are allowed and dialog-free. The client writes a job file, the always-on daemon runs it over the existing WebSocket, and writes a result file the client reads back. This is not a network call from the client, so the curl gate never fires and no MCP allowlist entry is needed. The three transports rank: file-bridge is the primary locked-down path, native MCP is the clean path when an admin allowlists the URL, and curl-on-18846 stays as a fallback. This is a genuinely different trust model from the agent running curl, so the intent of a curl gate should be confirmed with the admin before relying on it.
    Validated 2026-08-05 in a session under the managed policy: a `Write` then a `Read` ran with NO confirmation dialog. This is the load-bearing fact for the whole transport. The inbox watch is daemon-side (now event-driven, see #19), so it costs zero client tokens. The bridge also loads no MCP tool definitions and adds no JSON-RPC/SSE envelope, just raw shaped JSON. Client token rules live in `skills/file-bridge.md` (batch, read-once, shaped returns, screenshots to file).

16. **Name: `turbofig`, not `turbofig-mcp` (renamed 2026-08-05, commit `ddf680f`).**
    Why: the product is a multi-transport Figma-to-AI bridge. The file-bridge is the primary path, with MCP and curl as the other two transports (see #15). The `-mcp` suffix mislabeled it as MCP-only. The Cargo package, binary, and lib are all `turbofig`. Genuine MCP names are kept on purpose: the `/mcp` route, the `TURBOFIG_MCP_PORT` env var, `mcp-session-id`, and the MCP-endpoint prose. Positioning: "Turbofig, the always-on bridge from Figma to any AI agent." The GitHub repo rename and the local folder rename are manual steps outside the repo.

17. **Eval-first validated live in real Figma (2026-08-05).** The `EXECUTE` path builds its async function via `Object.getPrototypeOf(async()=>{}).constructor` (the Function constructor). This is permitted inside Figma's realm-isolated plugin sandbox and ran successfully (`return 1+1` -> 2, then full auto-layout node builds). This retires the single biggest eval-first risk; no fallback eval mechanism is needed.
    Also confirmed live and load-bearing: the plugin `manifest.json` REQUIRES `editorType` (set to `["figma"]`; it was missing and blocked import), and `networkAccess.allowedDomains: ["ws://localhost:18847"]` connects the plugin WebSocket with no dialog. The plugin bundle is a build artifact (`plugin/dist/code.js`, gitignored); rebuild with `bun run build` and reload the plugin in Figma after any plugin-source change.

18. **Reprioritized to an orchestration-first speed slice; Phase 4 deferred (2026-08-05).** Pulled the token/speed and orchestration levers forward from Phases 5-7 (the `tf` helper library, eval injection, shaped/firewall defaults, checkpoint/idempotency, `.claude/commands/design.md`) because they, not multi-file routing, address the "about an hour per complex page" pain.
    Why: wall-clock and token cost are dominated by per-call Claude round-trips, not the daemon or Figma. The fix is batching (many node ops per `execute`) plus parallel builder subagents that are firewalled so their screenshots and node dumps never reach the main context. Proven live: a landing page was planned, built by three parallel builders, auto-QA'd by a firewalled critic subagent, and auto-refined, in about seven Figma round-trips and a few minutes, with zero images in the main context. Batching does not hide the build: Figma renders each op live during a single eval. See the original phase plan's "Active priority" section (git history) and `.claude/commands/design.md`.

19. **File-bridge is event-driven (`notify` crate) with a 50ms backstop poll and an in-memory first-seen grace (2026-08-05).** The daemon wakes on filesystem events for the fast path and keeps a 50ms backstop for any dropped or delayed event. Supersedes the busy poll and the "50ms poll" wording in #15.
    Why 50ms and not slower: on macOS, FSEvents delivery latency is about 10-15ms, so a longer backstop made concurrent jobs behave near-sequentially. The real benefit of `notify` here is that the daemon wakes on a filesystem event instead of running a busy poll loop (sub-ms latency holds on Linux inotify). Race-safety keeps the single-write client contract: an unparseable job file is retried until `PARSE_GRACE` (200ms) elapses since first seen, tracked in an in-memory map rather than via mtime (a slow write or a skewed clock breaks mtime). A persistent claim failure now writes an error result so the client never hangs. Pulled forward from Phase 11.

20. **The console-mcp comparison is dropped; the ship gate is a self-baseline, not a "10x vs console-mcp" claim (2026-08-06).** Supersedes the comparison intent in #1, #7, #8, and the gate framing in #9 and the guiding principles.
    Why: the console-mcp baseline needed an external stack the user does not want to stand up, and the user does not want the comparison. The benchmark harness (`bench/harness.ts`) also drives only turbofig's file-bridge, so it never drove console-mcp. Rather than fabricate a competitor number (forbidden by the no-fabricated-baseline rule), the project keeps its own numbers as the reference budget.
    Self-baseline recorded (harness `--dry-run`, 2026-08-06): the `webpage` scenario is 5 jobs at 892 request tokens in (907 total); the `deck20` scenario is 3 jobs at 1461 request tokens in (1470 total). The dry-run measures true request-payload tokens (`ceil(chars/4)`); the tokens-out figure is the stub, not a live shaped return, and wall-time is meaningless under the stub. A future live run replaces tokens-out and wall-time with real values. These numbers are the regression budget for the Phase 13 CI guard.
    Still open (need a live run the user does not have now): the moodboard-to-website coherence verify (the original phase plan's Phase 7, see git history) and the metered main-context-tokens verify. The ship decision now rests on those qualitative live verifies, not on a numeric comparison gate.

21. **SUPERSEDED by #29 (2026-10-04). Taste is a swappable per-file "profile", not a single hardcoded baseline (2026-08-06, spike-driven).** Refines and extends #6 and #11.
    The lineup: three built-in profiles ship in the public build. `impeccable` is the default: a Figma-native adaptation of the anti-slop rules from the open-source `pbakaus/impeccable` skill (Apache 2.0, attributed), because impeccable targets frontend code and cannot be installed literally. `editorial` is art-directed (asymmetry, density, expressive type; from the `taste-skill` dial model). `minimal` designs in a genuinely minimal style AND carries the core anti-slop floor drawn from both impeccable and editorial. A user may also disable the profile ("none") or supply a custom one. The `emilkowalski` motion philosophy is out of scope, because static Figma does not render motion.
    Per-file, not per-session, is the ground truth. The choice persists in the Figma document via `figma.root.setPluginData("turbofig:profile", id)`, the only Figma primitive that travels with the file and survives reopen (`clientStorage` is per-user, wrong). This supersedes #11's per-session framing without conflict: the file holds the durable choice; the `conn_id`-keyed session registry is the runtime projection, populated from `FILE_INFO` on every connect. So N open files each run a different profile at once.
    Mechanism (tool surface stays at 4, no new tool):
    1. The plugin UI selector posts `SET_PROFILE`.
    2. The main thread writes `setPluginData` and re-emits `FILE_INFO` carrying `profileId`.
    3. The daemon stores `profile_id` on `PluginConn` and exposes the profile to eval code as `tf.taste`. The profile JS runs inside an IIFE so its internal `const taste` cannot collide with any top-level `taste` variable in user code.
    4. `turbofig_status` gains a `profileId` return field so `design.md` feeds the profile's constraints to the builder and critic subagents. Built-in profiles live in `skills/profiles/`; custom profiles load from `TURBOFIG_PROFILES_DIR` (default `~/.turbofig/profiles/`); the public build ships only the three built-ins, so no private pack enters the repo (satisfies #6 and the Phase 8 clean-separation item). The plugin selector is functional in Phase 8 and polished in Phase 9.

22. **Daemon supervision is fail-fast and locks recover from poisoning (2026-08-06, audit-driven).** `main` runs the three servers (MCP, WS, bridge) under `tokio::select!`: if any handle finishes for any reason, `main` logs which subsystem ended and calls `process::exit(1)`, so launchd `KeepAlive` only ever restarts a fully healthy daemon. `serve_bridge` now returns `Err` when its `notify` watcher channel closes (it returned `Ok` before, which silently stopped the bridge while the process stayed alive). All shared `std::sync::Mutex` locks use `.lock().unwrap_or_else(|e| e.into_inner())`, so one panic while holding a lock cannot cascade into a permanent routing outage.
    Why it matters: "always-on and never crash" is priority one, and the old `tokio::join!` plus the bridge `Ok` path let a whole transport die invisibly. Also from the same audit: Biome now lints `skills/**/*.js` with an override that turns off `noUnusedVariables` and `noApproximativeNumericConstant`, because a profile's `const taste` is injected into the eval context (intentionally unused in-file) and ratios like `1.414` are deliberate design data, not a misspelled `Math.SQRT2`.

23. **Two Figma plugin-load constraints, both load-bearing (2026-08-06, Phase 9 live test).** First, the Figma main-thread runtime rejects ES module syntax: a bundle with a top-level `export`/`import` fails to load. Both plugin bundles must be classic scripts, so `code.ts` builds with `--format=iife` and the UI `main.ts` builds as an IIFE via `build-ui.ts`. Second, `networkAccess.allowedDomains` rejects a wildcard port (`ws://localhost:*` is "not a valid URL"); Figma allows wildcards only for subdomains. To let the plugin follow a user-configurable `TURBOFIG_WS_PORT`, `allowedDomains` is set to `["*"]` (allow-all), the only static value that covers any port. This is broader than ideal but acceptable for a local dev plugin talking to `127.0.0.1`; the alternative is a fixed port allowlist that drops arbitrary configurability. Extends #17: the plugin now has two build artifacts, `plugin/dist/code.js` and `plugin/dist/ui.html` (the manifest `ui` points at the built `dist/ui.html`). Third constraint (2026-08-07): `figma.fileKey` is a private-plugin API. It returns `undefined` unless the manifest sets `"enablePrivatePluginApi": true`, regardless of whether a file is open (`figma.root.name` is always available, but the key is gated). Without the flag the panel received an empty `fileKey`, so `updateFileDisplay` hid the whole fileKey row and both copy buttons. The flag is set and guarded by `plugin/src/manifest.test.ts`. This works for the dev-install model (#4); a Figma Community listing would disable private APIs, but Turbofig ships as a dev-install. Fourth and fifth constraints (2026-08-07, live UI test), both load-bearing, do not revert: the panel receives the Figma theme variables (`--figma-color-*`) only when `figma.showUI` is called with `themeColors: true`; without it the panel renders on its white fallbacks and ignores dark mode. And `navigator.clipboard` is unreliable inside the plugin iframe (it silently rejects), so both copy buttons use a hidden `<textarea>` + `document.execCommand("copy")`; reverting either reintroduces a bug the user hit live.

24. **Multi-file targeting is by `fileKey`, never by port (clarified 2026-08-06).** One daemon serves every open file on one port; each file's plugin opens its own WebSocket and announces its `fileKey`. A call routes to a file by an explicit `fileKey` argument, else the session-to-file pairing, else the sole connected plugin. So a single open file needs no targeting; several open files need a `fileKey` (or a one-time pairing) per Claude session. The plugin port field is therefore advanced config only. Phase 10 acts on this: hide the port field, surface a full copyable `fileKey`, and make the connection model self-evident. Refines the routing in #14/#15 with the user-facing model.

29. **Taste removed from the product ahead of the public release (2026-10-04). Supersedes #6, #11, #21, and the taste parts of #25.** Taste (the `impeccable`/`editorial`/`minimal` profiles, `SET_PROFILE`, `tf.taste` injection, `TURBOFIG_PROFILES_DIR`, the plugin profile selector) is removed from the daemon, the plugin, and the docs. 30. **Origin validation on both ports, ahead of the public release (2026-10-04).** Neither port checked the Origin header: a malicious web page open in the user's browser could `fetch()` the MCP HTTP port or open the WebSocket port directly and drive `turbofig_execute` against whatever Figma file is open, with no prompt. Fixes, per the MCP spec's Origin-validation requirement: (a) the HTTP MCP port (18846) rejects any request carrying an Origin header with 403; a real MCP client (curl, a native MCP client, the file-bridge) never sends one, so this only blocks a browser. (b) The WebSocket port (18847) rejects the upgrade with 403 for any Origin other than absent or the literal `"null"`; the Figma plugin UI runs in a sandboxed iframe, which a browser reports as a null origin, so the real plugin still connects. A per-install handshake token is the next layer (the original phase plan's Phase 13, see git history) but is not built yet: Origin checking alone stops a web page, not a malicious local process. (c) The file-bridge directories (`~/.turbofig`, `inbox/`, `outbox/`) are set to mode 0700 on every daemon start, fixing an existing install's mode if it was created before this change or loosened by a permissive `umask`, because job and result files can carry arbitrary eval code and its output.

31. **SUPERSEDES #20 (2026-10-04, audit-driven bench rebuild). The console-mcp comparison is back in scope, and #20's `chars/4` figure was never "true request-payload tokens."** An external audit of `bench/` found both claims no longer held up: #20 said the comparison needed an external stack the user did not want to stand up, but `figma-console-mcp` is already installed and running for client work, behind `supergateway` on port 3846, so standing it up costs nothing extra. And #20's "true request-payload tokens" line described `ceil(chars / 4)` of the JSON envelope, which is a rough approximation, not a true count of anything; it also left out the per-session cost of loading tool schemas into an agent context, which does not show up in a payload at all.
    The rebuilt harness fixes both problems with two separate, honestly-labelled measurements instead of one approximate one: (a) a **transport layer** — exact wire bytes in and out per job (`bench/transports.ts`), never estimated, measured identically for all three targets (`turbofig-mcp`, `turbofig-bridge`, `console-mcp`); and (b) an **agent layer** (`bench/agent.ts`) — real input/output/cache token counts and turn counts from a headless `claude -p ... --output-format json` session per target, which is the only way to see the tool-schema loading cost the byte count misses. Only one Figma plugin runs per file at a time, so `bench/harness.ts` benchmarks one target per invocation and `bench/compare.ts` merges the separate reports. Scenarios now carry a `label` (`"transport"` for plain-Plugin-API jobs runnable on any target, `"transport + helpers"` for `tf.*`-helper jobs that only turbofig can run), so a published number never silently compares a helper library against a raw transport. `bench/baseline.json` is relabelled a static payload-size snapshot, not a claimed measurement (see also finding #8 in the audit this decision responds to).
    Still true from #20 and retained here: no fabricated competitor number. Every number in this decision and in any future README/LinkedIn post must come from an actual `--out` report or `agent.ts --out` report, never estimated or invented.
    Partially refined by #31-#33 (2026-10-04, pre-release audit): (c) now only chmods `inbox/` and `outbox/`, never `TURBOFIG_BRIDGE_DIR` itself (it can be a pre-existing, shared path the daemon does not own), and a failure to tighten the mode is logged rather than fatal to startup.

32. **The request-id counter starts at a random value, not 1 (2026-10-04, pre-release audit).** Request ids were a plain `AtomicU64` starting at 1 on every daemon start. Two problems followed from a fixed start: a `RESULT` for a stale id left over in the bridge outbox, or sent late by a just-restarted plugin, could collide with a freshly issued id from the new run; and the ids were trivially guessable, which mattered once resolving a `RESULT` depended on more than the id alone (see #33's ownership check). Fix: `AppState` now seeds its counter at a value drawn from `[1, 2^40)` at construction, using `std::collections::hash_map::RandomState`'s OS-seeded SipHash keys so no `rand` dependency is needed. `2^40` keeps every id a JS-safe integer even after billions of requests. This does not replace the ownership check in #33, it removes the easier of the two routes to forging or colliding a `RESULT`.

33. **A `RESULT` must be bound to the connection its request was sent on (2026-10-04, pre-release audit).** `resolve(id, value)` trusted any connection that sent a well-formed `RESULT` frame carrying a known `requestId`, with no check on which connection sent it. Since the WebSocket port accepts any null-origin connection (needed for the Figma plugin iframe, see #30b), a malicious web page's own WebSocket could guess or enumerate a live `requestId` and answer another file's in-flight call. Fix: the pending map now stores `(conn_id, sender)`; `resolve(id, conn_id, value)` only fires the sender when the calling connection's id matches the one the request was registered under, and silently drops a mismatched reply so its rightful owner can still answer later. Registration and the connection's liveness check now happen under one lock (`register_pending_if_connected`), closing a second, narrower race: a socket closing between route resolution and pending registration could otherwise leave an orphaned pending entry that only the full request timeout would clear.

34. **PARTIALLY SUPERSEDED by #35 and #36 (2026-10-04 second-round audit): the "`EXECUTE`-only timeoutMs" line below no longer holds; see #36.** Protocol contract for the plugin-side rework, shared across the Rust and plugin PRs built in parallel (2026-10-04, pre-release audit). The daemon and plugin builders worked from the same contract, recorded here so neither drifts:
    - `EXECUTE` carries a `timeoutMs` field: the daemon's own request timeout, in milliseconds. The plugin must stop waiting and reply `ok:false` once `timeoutMs` elapses, rather than leave the daemon's request hanging. The daemon itself waits `timeoutMs + 1000ms` before giving up, so the plugin's own "I gave up" reply (more informative than a bare daemon-side timeout) usually wins the race. This only applies to `EXECUTE`: `STATUS`, `GET_SELECTION`, and `SCREENSHOT` keep the daemon's plain request timeout, since those ops cannot run long user code.
    - Request ids are the random-start, JS-safe counter from #31, on both sides of the wire.
    - The plugin caps a serialized `RESULT` at 16 MiB and replies `ok:false` above that, so one oversized export can never wedge the socket. The daemon's own WebSocket message and frame size caps are 32 MiB (see #30b's successor hardening), giving headroom above the plugin's cap rather than matching it exactly.
    - `STATUS` must not queue behind a long-running job: the plugin runs `EXECUTE`, `GET_SELECTION`, and `SCREENSHOT` one at a time, FIFO, so a liveness check never silently times out just because an `EXECUTE` is mid-flight.
    A timeout error returned to the caller (by any of the four ops, not only `EXECUTE`) now names the `requestId` and states that the job may still be running in Figma and that a retry is not idempotent: a bare "plugin timed out" invited a caller to retry a call that might still land, duplicating the effect.

35. **SUPERSEDES the "evicts the older connection" fileKey model from #24 (2026-10-04, second-round pre-release audit).** A duplicate-`fileKey` connection (a reconnect, or a second window on the same file) used to evict the older entry from the registry. That broke two ways: eviction never closed the old socket (`ws.rs` kept its `tx` clone), so a later `FILE_INFO` from the evicted connection, for example both windows re-announcing after a file rename, could remove the *live* connection and lose the file's route entirely; and eviction cancelled the evicted connection's in-flight jobs, which were still legitimately running in Figma. Fix: remove eviction. Every live connection stays registered, even sharing a `fileKey`. Routing (`connections_named`) resolves which one to use by picking the newest (highest conn_id) live connection for a given key, and dedupes a shared key in both the Ambiguous list and status output, so a caller still never sees the same file listed twice or reported as ambiguous. When a connection closes, only its own entry is removed, so routing falls back to an older window for that file if it is still open. A message from a conn_id no longer in the registry (FILE_INFO or RESULT) is now explicitly ignored, closing the only remaining way a dead or forged connection could touch live state.

36. **Queue deadline is stamped at enqueue time, and GET_SELECTION/SCREENSHOT now race it too (2026-10-04, second-round pre-release audit).** Two related plugin-side gaps, found together: (a) the plugin's per-job timeout was effectively measured from when a job started running (dequeue time), not from when the daemon's message was received (enqueue time), so a job queued for a long time behind a slow one got a fresh full timeoutMs budget instead of whatever was left of its real deadline. (b) Only `EXECUTE` raced its run against a timer; `GET_SELECTION` and `SCREENSHOT` had no timeout race at all, so a hung `exportAsync` or `getNodeByIdAsync` blocked the FIFO queue forever. Fix: `createDispatcher`'s `enqueue` now stamps `deadline = Date.now() + timeoutMs` (default 30000 when `timeoutMs` is absent) at the moment the message is enqueued, for all three queued types. If that deadline has already passed when the job reaches the front of the queue, it never runs; the plugin replies `ok:false` with "expired in the queue; the job did not run", so a caller knows a retry is safe. Otherwise the job races against whatever time remains until the deadline. This retires the `EXECUTE`-only line in #34: all three queued ops now carry `timeoutMs` from the daemon and are raced the same way. `timeoutMs` is clamped to `2^31 - 1` ms independently on both sides of the wire (the daemon's `TURBOFIG_REQUEST_TIMEOUT_MS`, clamped to 600000ms with a logged warning past that; and the plugin's own `setTimeout` calls), since a larger value overflows a JS `setTimeout` and fires almost immediately instead of waiting. Separately, the queue's chained promise (`queueTail`) now attaches a `.catch` to every enqueued link, so a `job()` or `post()` throw in one job can never leave the chain permanently rejected and silently drop every job queued after it.

37. **File-bridge: a schema-invalid job fails at once, and a job id is a documented unique-per-job contract (2026-10-04, second-round pre-release audit).** Two related bridge gaps. (a) A job file that read and parsed as JSON but failed the `Job` schema (an unknown op, a bad field) went through the same `PARSE_GRACE`-then-backstop path as a genuinely half-written file, so its caller waited out that grace window before getting an error it could have had immediately. A complete, schema-invalid file is a final answer, not a "maybe still writing" state, so it is now rejected the moment it fails to parse into a `Job`, with no grace wait. (b) Claiming a job (removing its inbox file) and deleting any stale same-id outbox result was not race-free against a client that reused an id while the first job with that id was still running in its own `tokio::spawn` task. Fix: a shared in-flight id set, checked before a job is claimed; a duplicate id still in flight is left untouched in the inbox (not claimed, not answered) until the first job's task finishes and removes its id, so neither job's `.tmp` file or result can ever collide. This makes "a job id is unique per job, never reused while in flight" a documented client contract, not an assumption: `skills/file-bridge.md`, `helpers/tf-api.md`, and the plugin's connect prompt all now say so.

38. **SUPERSEDED by #43 (2026-10-05): the "future `turbofig setup` command" line below never shipped; the daemon's own startup writes these files on every start instead. The Figma plugin is embedded into the daemon binary at compile time (2026-10-05, ahead of the public GitHub/Homebrew release).** A Homebrew-installed daemon has no copy of this repo to read `plugin/dist/` from, so a future `turbofig setup` command (not built yet) needs the plugin files available from inside the binary itself. `daemon/build.rs` embeds `plugin/manifest.json`, `plugin/dist/code.js`, and `plugin/dist/ui.html` via `include_str!` into a generated `OUT_DIR` file, read by `daemon/src/embedded.rs`'s `embedded_plugin()`. The plugin is a separate Bun/TypeScript build, not a Cargo artifact, so a Rust-only contributor and the CI Rust job (which never runs Bun) must still be able to `cargo build`: when `plugin/dist` is missing, `build.rs` prints a `cargo:warning` and generates a stub, so `embedded_plugin()` returns `None` instead of failing the build. The CI TypeScript job, which does build the plugin, gained one extra step (`cargo build` after "Build plugin") so the embedded path still compiles against a real `plugin/dist` somewhere in CI. `daemon/src/plugin_files.rs`'s `write_plugin_files(home, token)` is the write-to-disk half: it writes the three embedded files to `<home>/figma-plugin/`, injecting the real pairing token into `ui.html` (see #39) in place of the `__TURBOFIG_PAIRING_TOKEN__` placeholder the embedded build always carries, and a version+token-hash marker file so `plugin_files_outdated` can detect a stale copy after a daemon upgrade or a token rotation without storing the token twice. `turbofig setup`, the command that calls this on a user's machine, is out of scope here; this entry covers only the parts it will call.

39. **The plugin WebSocket upgrade requires a per-install pairing token, closing a null-Origin gap (2026-10-05, ahead of the public release; builds out the original phase plan's Phase 13 token item, see git history).** Origin validation (#30) stops a normal browser `fetch()` or WebSocket connect, but a sandboxed `<iframe>` on any web page reports Origin `null`, the exact value the real Figma plugin UI reports (it also runs in a sandboxed iframe), so Origin checking alone cannot tell the two apart: a malicious page could open the plugin socket and receive the AI's jobs. Fix: `<home>/token` (32 random bytes, hex-encoded, mode 0600) is created on first daemon start and never overwritten; the WS upgrade now requires a `token` query parameter matching it, checked in constant time, after the existing Origin check, before the upgrade completes (401, not just a closed socket). Token generation (`token::random_token_hex`, no new crate: four `RandomState`-seeded `SipHash` draws stitched together, the same OS-CSPRNG technique #32 already uses for the request-id counter) is split from persistence (`token::ensure_token`, the only path that touches a real `~/.turbofig/token`): `AppState::new`/`with_timeout` generate a token in memory, so every existing test (and the ~50 mock-plugin WS connects across `daemon/tests/`) keeps working unchanged in spirit, just appending `?token={}` to the connect URL, and never touches disk. Only `main.rs` calls `ensure_token` and builds the production `AppState` via `new_with_token`. The token is never logged, never returned by `turbofig_status`, and never appears in an error message (enforced by `test_turbofig_status_never_includes_the_token`). On the plugin side, `plugin/src/ui/ui-logic.ts`'s `wsUrlForPort(port, token)` appends the token to every connect and reconnect URL, including after a port switch, since `main.ts` has exactly one `connect()` function all three paths share. The embedded `dist/ui.html` always carries the token as the build-time constant `__TURBOFIG_PAIRING_TOKEN__`; see `plugin/build-ui.ts`'s own design note for how a real token reaches a local dev build without ever reaching git or a release binary.

40. **SUPERSEDED by #43 (2026-10-05): `setup` itself was replaced by the daemon's own on-demand startup, and launchd autostart is now optional rather than what `setup` installed by default; the pure-logic-plus-seams approach to the CLI below still stands. The CLI (`clap`) owns install/ops as subcommands, not separate binaries or shell scripts, and `setup`/`uninstall` are pure-logic-plus-seams (2026-10-05, closes out #38's "out of scope here").** `turbofig` with no subcommand still just runs the daemon (`serve` is its explicit alias), so nothing about the existing Homebrew-formula invocation or the plist this decision adds needs to change shape. `setup`/`uninstall`/`status` live in `daemon/src/cli.rs` as functions that take their real-world dependencies as arguments (`home`, `launch_agents_dir`, a `&dyn Launchctl`, the uid, `current_exe`) rather than reading them from the environment directly, so every branch is unit-testable with a temp dir and a fake `Launchctl` (`daemon/src/launchd.rs`) instead of the real `~/Library/LaunchAgents` or a real `launchctl bootstrap` against the user's `gui/<uid>` session; `main.rs` is the only place that supplies the real values. `setup` is written to be safely re-run: `ensure_token` never overwrites, `write_plugin_files` always overwrites deterministically given the same token, the plist is byte-identical given the same binary path and home, and `bootout` (ignoring "not loaded") then `bootstrap` gives the same end state whether or not the service was already loaded. The plist's `ProgramArguments` points at the *stable* binary path, not `current_exe` verbatim: Homebrew's `Cellar/turbofig/<version>/...` path disappears on every upgrade, but the `<prefix>/bin/turbofig` symlink it maintains alongside it does not (`launchd::stable_binary_path`, matched on a canonicalized `/Cellar/turbofig/` substring so it covers both the Intel (`/usr/local`) and Apple Silicon (`/opt/homebrew`) default prefixes). `GET /health` is the machine-readable half `turbofig status` calls over plain HTTP (reqwest), reusing `AppState::named_connections_json` so it can never drift from `turbofig_status`'s own connected-files shape or accidentally gain the token.

41. **Supervised restart drains in place instead of letting `KeepAlive` kill an in-flight job mid-upgrade (2026-10-05).** Without this, a `brew upgrade` that replaces the Cellar symlink mid-session would only take effect on the *next* `KeepAlive` restart (a crash, or the next manual stop), and if that restart happened to land during a long `turbofig_execute` call, the job would simply vanish with no retry signal beyond the generic timeout error. Fix: the plist from #40 sets `TURBOFIG_SUPERVISED=1`; when set, `main.rs` spawns a loop that polls the stable binary path (the same rule #40 introduced) every 30s and compares its canonical target against the one resolved at daemon startup (`supervisor::upgrade_detected`, a plain path comparison extracted so it needs no real filesystem or sleep to test). On a change, the daemon sets `AppState::draining`, which `resolve_route` checks first and refuses with a new `RouteError::Draining` before even picking a target connection — a single chokepoint, since all four ops (`run_status`/`run_execute`/`run_get_selection`/`run_screenshot`) across all three transports (MCP, file-bridge, and the WS-routed call itself) already funnel through `resolve_route`. The daemon then waits up to 60s (`supervisor::wait_for_drain`, polling `AppState::jobs_in_flight`, the pending-request map's live count) for whatever was already in flight to finish, then exits 0 either way: a timed-out drain's abandoned jobs are no worse off than an ordinary `KeepAlive` restart would have left them, and launchd starts the new binary on the exit either way. 30s/60s are not configurable: this is an operational safety net, not a product-facing tunable, and an extra env var here would be another thing `turbofig setup`'s users never need to touch.

42. **Packaging-review hardening: `--purge` deletes known entries only, the plist carries setup-time env vars, and an unresolved binary path never counts as an upgrade (2026-10-05, first public-release review).** Three related gaps, all in the install/uninstall/supervised-restart path #40 and #41 built, found in the same review pass.
    `turbofig uninstall --purge` called `remove_dir_all` on `home` directly. `home` is `TURBOFIG_BRIDGE_DIR`-controlled, so a user who pointed it at a shared folder, or left it unset in a shell where `HOME` resolved oddly, could lose far more than turbofig's own files. Fix: `cli::purge_home` deletes only the fixed list of entries turbofig itself ever writes (`token`, `figma-plugin/`, `inbox/`, `outbox/`, `daemon.log`), then removes the directory itself only if that leaves it empty. An unrelated file left in `home` now survives `--purge` by construction, not by convention.
    The plist #40 writes set only `TURBOFIG_SUPERVISED=1` in `EnvironmentVariables`, so `TURBOFIG_BRIDGE_DIR=/x turbofig setup` wrote the token and plugin files under `/x`, but the launchd-started daemon, with no such override in its own environment, ran against the default `~/.turbofig` and the plugin got a 401 on every connect. Any `TURBOFIG_*_PORT` or `TURBOFIG_REQUEST_TIMEOUT_MS` override given to `setup` was lost the same way. Fix: `launchd::carry_over_turbofig_env` collects every `TURBOFIG_*` variable set in `setup`'s own environment, except `TURBOFIG_SUPERVISED` (the daemon sets its own) and the setup-only `TURBOFIG_LAUNCH_AGENTS_DIR`, and `plist_contents` writes each one into `EnvironmentVariables` alongside it. `setup` prints one line naming whatever was carried over, so a custom override is visible, not silent.
    `supervisor::installed_target` fell back to the stable path itself when `canonicalize` failed, which can never equal the baseline, so a resolve failure during the brief window mid-`brew upgrade` where the Cellar symlink target is momentarily gone counted as "an upgrade happened" and triggered a spurious drain-and-restart; after `brew uninstall` removed the binary entirely, the same fallback made every check look like a fresh upgrade forever, so the daemon exited 0 in a loop and launchd kept retrying a `ProgramArguments` path that no longer existed. Fix: `installed_target` now returns `Option<PathBuf>`, `None` on a resolve failure, and `upgrade_detected` treats `None` as "cannot tell, skip this check", never as a difference from the baseline. After 3 consecutive unresolved checks, the daemon logs a line saying the binary is gone, so a user watching the log (rather than just seeing a silently respawning process) knows to run `turbofig uninstall` or reinstall.

43. **Install model: on-demand daemon started by `turbofig mcp` or `turbofig`; launchd autostart optional (2026-10-05, supersedes #38 and #40).** `turbofig setup` (planned in #38, built in #40) never shipped as the install step: it tied "the daemon has a token and plugin files" to a one-time command the user had to remember to run, and it installed launchd autostart by default, which is more than a user asking "bridge Figma to my AI agent" needs. Fix: the daemon's own startup (`run_daemon`) always ensures the token and always writes or refreshes `<home>/figma-plugin/`, whether it was started by `turbofig mcp` (a native MCP client's own `claude mcp add turbofig -- turbofig mcp`, the common case: an agent starting the daemon the first time it is asked to use Figma), by the bare `turbofig` command (a human running it once to see the first-run walkthrough), or by `turbofig serve`/`start` directly. `spawn::spawn_detached_daemon` is the one on-demand start path all of these share. `turbofig autostart on`/`off` still exist, for a user who wants the daemon to survive a reboot without a client starting it first, but nothing above depends on autostart being on: the on-demand start is what makes `brew install LukeHawkins/tap/turbofig` followed immediately by `claude mcp add turbofig -- turbofig mcp` just work, with no separate install step and no plist in between. The `<home>/plugin-seen` marker (`plugin_files::mark_plugin_seen`, written on the first valid-token plugin WebSocket connect) is what lets the bare `turbofig` command tell a genuine first run from a later one without a separate on-disk "setup ran" flag.

44. **A clean `turbofig stop` must not be restarted by autostart; a supervised upgrade restart must (2026-10-05, supersedes the `KeepAlive: true` and plain `exit(0)` parts of #38, #40, and #41).** Those earlier entries described the autostart plist's `KeepAlive` as plain `true` and the supervised-restart and `/control` restart paths as exiting 0. Plain `KeepAlive: true` cannot tell "the user asked for this to stop" apart from "this crashed": launchd restarts either one, so `turbofig stop` under autostart looked like it didn't work. Fix: the plist now sets `KeepAlive: {SuccessfulExit: false}` (`launchd.rs`), so launchd restarts the daemon on a crash (any non-zero exit) but leaves it stopped after a clean exit 0 until the next login. This only works if the paths that *should* restart exit non-zero: the supervised-upgrade loop and a supervised `/control restart` now both exit `supervisor::SUPERVISED_RESTART_EXIT_CODE` (75), not 0, so `KeepAlive` restarts them with the upgraded binary; `/control stop`, and an unsupervised `/control restart`, still exit 0, since nothing is watching to restart the latter and the caller starts the new process itself. `turbofig stop` also now fails instead of silently doing nothing: if `/health` answers but the token file is missing or no longer matches, `/control` cannot authenticate, so `stop` exits 1 and names `pkill -f 'turbofig serve'` as the fallback, rather than reporting the same idempotent "nothing running" success it reports when there truly is no daemon.

45. **`POST /job` and `POST /mcp` now require the pairing token, like `/control` (2026-10-05, supersedes the "the HTTP MCP port still has no token" position in #30 and #39).** Those entries left the HTTP MCP port tokenless by design: another local process already shares the same user's trust boundary, so a token on disk gave it no real protection it did not already have by reading the file. That reasoning held for the same-user case, but it did not cover a *different* macOS account on the same Mac: that account can still reach `127.0.0.1`, but it cannot read a different user's `~/.turbofig/token`, so a token on `/job` and `/mcp` closes a real gap #30 and #39 left open. Fix: `mcp.rs`'s `require_bearer_token` middleware now gates both routes, matching `/control`'s existing check; a missing or wrong token gets 401. `GET /health` gets a lighter-touch version instead of the same gate: it always answers (reporting liveness to an unauthenticated caller is the point of `/health`), but returns only `version` and `uptimeSeconds` without a valid token, and the full payload (`connectedFiles`, `pid`) with one. The cost to the default agent path is near zero: the stdio proxy already reads the token from disk to start the daemon, so it reads it for `/job` too and no user-facing step changes. The file-bridge stays tokenless; its protection is its directory mode (0700, see #30c), not a header.
