# Decisions

1. **Eval-first, ~4 tools (turbofig_execute / turbofig_get_selection / turbofig_screenshot / turbofig_status).**
   Why: token economy (~96% less tool-def load), resilience (new Figma APIs work same-day), full capability through one tool. Baseline competitor figma-console-mcp already has eval + multi-file; we win on DX, performance, Rust single-binary, and true always-on.

2. **Rust daemon via rmcp 3.1.0 (transport-streamable-http-server) + legacy_session_mode.**
   Why: client uses 2025-03-26 spec with mcp-session-id; rmcp defaults to the session-less 2026-07-28 spec. `legacy_session_mode: true` on `StreamableHttpServerConfig` with `LocalSessionManager` makes rmcp issue the `mcp-session-id` header on `initialize` and require it on subsequent calls.
   Phase 1 result: CONFIRMED. `initialize` returns `mcp-session-id`; subsequent calls reuse it; responses are SSE `data:` lines. A Rust integration test (`daemon/tests/transport.rs`) and a curl script (`scripts/handshake.sh`) both pass. The rmcp #1108 risk is retired.
   Fallback (retained, not needed now): if a future rmcp release breaks `legacy_session_mode`, hand-roll the transport with axum. Add a POST `/mcp` handler that assigns an `mcp-session-id` on `initialize`, stores session state in an in-memory map, and streams SSE `data:` responses. The WebSocket connection to the plugin stays on axum regardless. This is a drop-in replacement because the daemon already owns the axum `Router`.

3. **Ports are a product contract: default HTTP 18846, WS 18847, env-overridable (TURBOFIG_MCP_PORT / TURBOFIG_WS_PORT).**
   Why: obscure ports below 32768 avoid conflicts. The OS auto-assigns ephemeral ports at or above 32768 (Linux default 32768-60999, macOS 49152+), so a fixed server port there can collide. 18846 and 18847 sit below that floor, so the OS never auto-assigns them, and they are uncommon dev ports. A user with a conflict overrides both with one env var. This supersedes the earlier 3846/3847 choice; curl skills that targeted 3846 must update to 18846 (see Phase 11).

4. **eval blocks a Figma Community store listing; ship as dev-install.**
   Why: review rejects arbitrary server-run code. Keep the plugin hybrid-ready: a {type} dispatch table so a community-safe command vocabulary build is additive later with no rework.

5. **Distribution: primary `npx turbofig` using per-platform binary packages as optionalDependencies (the esbuild/Biome pattern).**
   Why: no postinstall network fetch, works on locked-down corporate networks. Secondary: cargo install, Homebrew tap, GitHub Release binaries + curl|sh. Daemon nudges on a newer version; plugin warns on version mismatch.

6. **Trainability: ship a generic good-designer taste baseline; user brand/project packs load on top and switch at runtime.**
   Why: the public build ships only the generic baseline, never private packs.

7. **Token strategy: subagent context firewall (screenshots live in disposable subagents), downscaled + milestone-only screenshots, shaped ids-first returns, batched execute.**
   Why: the whole product pitch is token economy. Every design decision is judged on token cost.

8. **Multi-file: true routing by fileKey (N independent sessions <-> N files), stronger than console-mcp's broadcast execute_across_files.**
   Why: per-session isolation is a hard requirement for concurrent multi-file design work.
   Phase 4 result: DELIVERED. The daemon holds a `conn_id`-keyed connection registry (one WebSocket per open file) and a `mcp-session-id` -> `fileKey` pairing map. `resolve_route(session_id, file_key)` in `daemon/src/lib.rs` picks the target by explicit `fileKey`, then the session pairing, then the sole named connection, and returns a clear no-plugin, ambiguous, or not-found error. A socket close cancels only that connection's pending requests, so files stay isolated. Two non-obvious mechanism facts: (a) a tool reads the session id via `Extension<http::request::Parts>` (rmcp 3.1.0 injects the HTTP parts into the request context; needs the `http` crate) and reads the `mcp-session-id` header; (b) an empty `mcp-session-id` header or an empty `fileKey` argument is normalized to no-target, so an empty string never records a bogus shared pairing and never forces a spurious not-found. Each of the 4 tools gained an optional `fileKey` argument; the tool surface stays at 4.

9. **Ship gate placement: Phase 5 is a provisional baseline only. The binding "far better than console-mcp" gate runs after Phase 7.**
   Why: the token and speed wins come from the helper library, the design-worker orchestration, and the subagent firewall added in Phases 6 and 7. Gating at Phase 5 would measure the system without its main levers.

10. **Context firewall is enforced, not just convention. Inline screenshots need an explicit opt-in and warn past a budget. File-mode plus subagent-read is the default path. Large reads without depth or fields are capped or warned.**
    Why: for a redistributed product the token promise cannot depend on client prompt discipline alone.
    Built in Phase 5: the "cap or warn" choice is an advisory `warning` field, never truncation. A read over `READ_BUDGET_BYTES` (20000) or an inline screenshot over `INLINE_SCREENSHOT_BUDGET_BYTES` (100000) gains a `warning` that names the remedy; the daemon never drops data, because truncating an `execute` result could corrupt it. Screenshots downscale to a longest-edge cap (`maxDim`, default 1200, floored at 1) via the `image` crate, and default to file mode; `fullRes` plus `return:"inline"` is the only high-res path. Read shaping is additive: `get_selection` keeps its seven-field base shape and adds opt-in `fields` and `depth` (capped at 5; `children` is reserved for the depth mechanism).

11. **Brand packs bind per session, keyed like the routing registry.**
    Why: concurrent multi-file sessions may need different brands at once, so a single global active pack would break isolation.

12. **Daemon lifecycle: launchd KeepAlive restarts the daemon on crash. Every call has a daemon-side timeout so a silent plugin never hangs a request. On restart the in-memory session registry is lost, so clients get a clear reinitialize signal rather than a silent error.**
    Why: always-on reliability requires automatic restart and clean failure signalling.

13. **eval security for redistribution: the daemon binds to 127.0.0.1 only. eval has resource guards beyond the timeout (runaway loop and memory). The prompt-injection and file-exfiltration risk is documented, because arbitrary eval on a user's open file is powerful. Acceptable for local use, called out for redistributed use.**
    Why: local-only binding limits the attack surface; documented risk keeps redistributors informed.
    DNS-rebinding defence (Phase 1, deliberate): rmcp `StreamableHttpServerConfig` defaults `allowed_hosts` to `["localhost", "127.0.0.1", "::1"]`. This rejects a spoofed `Host` header with 403, so a browser page on a rebound domain cannot reach the loopback endpoint. We keep this default on purpose. We do NOT narrow it to `127.0.0.1:<port>` because curl skills may use `localhost`. `allowed_origins` stays empty (Origin validation skipped) because there is no browser client and the `Host` allow-list already blocks the browser attack path. Revisit `allowed_origins` if a browser client is ever added.

14. **Long-job durability: the daemon runs decoupled from any client session, so a session end or client crash never kills an in-flight job. Long design jobs checkpoint the plan spec and per-section progress to disk, and resume from the last completed section. Operations are idempotent, keyed by stable node id, so a resume never duplicates.**
    Why: the current supergateway stack dies with the session (SIGTERM), leaving big jobs half done. Decoupling plus checkpoint and resume lets a huge job survive a restart with completed work intact.

15. **File-bridge transport: the daemon services a watched folder (`~/.turbofig/inbox` -> `outbox`, env `TURBOFIG_BRIDGE_DIR`) so a client drives it with local file writes and reads only. Result files are written atomically (temp then rename).**
    Why: a locked-down Claude Enterprise policy forces a confirmation dialog on every curl and blocks self-adding an MCP server (tested 2026-08-05: `claude mcp add` returns "not allowed by enterprise policy"). The Write and Read tools are allowed and dialog-free. The client writes a job file, the always-on daemon runs it over the existing WebSocket, and writes a result file the client reads back. This is not a network call from the client, so the curl gate never fires and no MCP allowlist entry is needed. The three transports rank: file-bridge is the primary locked-down path, native MCP is the clean path when an admin allowlists the URL, and curl-on-18846 stays as a fallback. This is a genuinely different trust model from the agent running curl, so the intent of a curl gate should be confirmed with the admin before relying on it.
    Validated 2026-08-05 in a session under the managed policy: a `Write` then a `Read` ran with NO confirmation dialog. This is the load-bearing fact for the whole transport. The inbox watch is daemon-side (now event-driven, see #19), so it costs zero client tokens. The bridge is also the most token-light transport: no MCP tool definitions to load and no JSON-RPC/SSE envelope, just raw shaped JSON. Client token rules live in `skills/file-bridge.md` (batch, read-once, shaped returns, screenshots to file).

16. **Name: `turbofig`, not `turbofig-mcp` (renamed 2026-08-05, commit `ddf680f`).**
    Why: the product is a multi-transport Figma-to-AI bridge. The file-bridge is the primary path, with MCP and curl as the other two transports (see #15). The `-mcp` suffix mislabeled it as MCP-only. The Cargo package, binary, and lib are all `turbofig`. Genuine MCP names are kept on purpose: the `/mcp` route, the `TURBOFIG_MCP_PORT` env var, `mcp-session-id`, and the MCP-endpoint prose. Positioning: "Turbofig, the always-on bridge from Figma to any AI agent." The GitHub repo rename and the local folder rename are manual steps outside the repo.

17. **Eval-first validated live in real Figma (2026-08-05).** The `EXECUTE` path builds its async function via `Object.getPrototypeOf(async()=>{}).constructor` (the Function constructor). This is permitted inside Figma's realm-isolated plugin sandbox and ran successfully (`return 1+1` -> 2, then full auto-layout node builds). This retires the single biggest eval-first risk; no fallback eval mechanism is needed.
    Also confirmed live and load-bearing: the plugin `manifest.json` REQUIRES `editorType` (set to `["figma"]`; it was missing and blocked import), and `networkAccess.allowedDomains: ["ws://localhost:18847"]` connects the plugin WebSocket with no dialog. The plugin bundle is a build artifact (`plugin/dist/code.js`, gitignored); rebuild with `bun run build` and reload the plugin in Figma after any plugin-source change.

18. **Reprioritized to an orchestration-first speed slice; Phase 4 deferred (2026-08-05).** Pulled the token/speed and orchestration levers forward from Phases 5-7 (the `tf` helper library, eval injection, shaped/firewall defaults, checkpoint/idempotency, `.claude/commands/design.md`) because they, not multi-file routing, address the "about an hour per complex page" pain.
    Why: wall-clock and token cost are dominated by per-call Claude round-trips, not the daemon or Figma. The fix is batching (many node ops per `execute`) plus parallel builder subagents that are firewalled so their screenshots and node dumps never reach the main context. Proven live: a landing page was planned, built by three parallel builders, auto-QA'd by a firewalled critic subagent, and auto-refined, in about seven Figma round-trips and a few minutes, with zero images in the main context. Batching does not hide the build: Figma renders each op live during a single eval. See the "Active priority" section in `PLAN.md` and `.claude/commands/design.md`.

19. **File-bridge is event-driven (`notify` crate) with a 50ms backstop poll and an in-memory first-seen grace (2026-08-05).** The daemon wakes on filesystem events for the fast path and keeps a 50ms backstop for any dropped or delayed event. Supersedes the busy poll and the "50ms poll" wording in #15.
    Why 50ms and not slower: on macOS, FSEvents delivery latency is about 10-15ms, so a longer backstop made concurrent jobs behave near-sequentially. The real win of `notify` here is near-zero idle CPU, not sub-millisecond latency (sub-ms holds on Linux inotify). Race-safety keeps the single-write client contract: an unparseable job file is retried until `PARSE_GRACE` (200ms) elapses since first seen, tracked in an in-memory map rather than via mtime (a slow write or a skewed clock breaks mtime). A persistent claim failure now writes an error result so the client never hangs. Pulled forward from Phase 11.

20. **The console-mcp comparison is dropped; the ship gate is a self-baseline, not a "10x vs console-mcp" claim (2026-08-06).** Supersedes the comparison intent in #1, #7, #8, and the gate framing in #9 and the guiding principles.
    Why: the console-mcp baseline needed an external stack the user does not want to stand up, and the user does not want the comparison. The benchmark harness (`bench/harness.ts`) also drives only turbofig's file-bridge, so it never drove console-mcp. Rather than fabricate a competitor number (forbidden by the no-fabricated-baseline rule), the project keeps its own numbers as the reference budget.
    Self-baseline recorded (harness `--dry-run`, 2026-08-06): the `webpage` scenario is 5 jobs at 892 request tokens in (907 total); the `deck20` scenario is 3 jobs at 1461 request tokens in (1470 total). The dry-run measures true request-payload tokens (`ceil(chars/4)`); the tokens-out figure is the stub, not a live shaped return, and wall-time is meaningless under the stub. A future live run replaces tokens-out and wall-time with real values. These numbers are the regression budget for the Phase 13 CI guard.
    Still open (need a live run the user does not have now): the moodboard-to-website coherence verify (PLAN.md Phase 7) and the metered main-context-tokens verify. The ship decision now rests on those qualitative live verifies, not on a numeric comparison gate.

21. **Taste is a swappable per-file "profile", not a single hardcoded baseline (2026-08-06, spike-driven).** Refines and extends #6 and #11.
    The lineup: three built-in profiles ship in the public build. `impeccable` is the default: a Figma-native adaptation of the anti-slop rules from the open-source `pbakaus/impeccable` skill (Apache 2.0, attributed), because impeccable targets frontend code and cannot be installed literally. `editorial` is art-directed (asymmetry, density, expressive type; from the `taste-skill` dial model). `minimal` designs in a genuinely minimal style AND carries the core anti-slop floor drawn from both impeccable and editorial. A user may also disable the profile ("none") or supply a custom one. The `emilkowalski` motion philosophy is out of scope, because static Figma does not render motion.
    Per-file, not per-session, is the ground truth. The choice persists in the Figma document via `figma.root.setPluginData("turbofig:profile", id)`, the only Figma primitive that travels with the file and survives reopen (`clientStorage` is per-user, wrong). This supersedes #11's per-session framing without conflict: the file holds the durable choice; the `conn_id`-keyed session registry is the runtime projection, populated from `FILE_INFO` on every connect. So N open files each run a different profile at once.
    Mechanism (tool surface stays at 4, no new tool):
    1. The plugin UI selector posts `SET_PROFILE`.
    2. The main thread writes `setPluginData` and re-emits `FILE_INFO` carrying `profileId`.
    3. The daemon stores `profile_id` on `PluginConn` and exposes the profile to eval code as `tf.taste`. The profile JS runs inside an IIFE so its internal `const taste` cannot collide with any top-level `taste` variable in user code.
    4. `turbofig_status` gains a `profileId` return field so `design.md` feeds the profile's constraints to the builder and critic subagents. Built-in profiles live in `skills/profiles/`; custom profiles load from `TURBOFIG_PROFILES_DIR` (default `~/.turbofig/profiles/`); the public build ships only the three built-ins, so no private pack enters the repo (satisfies #6 and the Phase 8 clean-separation item). The plugin selector is functional in Phase 8 and polished in Phase 9.

22. **Daemon supervision is fail-fast and locks recover from poisoning (2026-08-06, audit-driven).** `main` runs the three servers (MCP, WS, bridge) under `tokio::select!`: if any handle finishes for any reason, `main` logs which subsystem ended and calls `process::exit(1)`, so launchd `KeepAlive` only ever restarts a fully healthy daemon. `serve_bridge` now returns `Err` when its `notify` watcher channel closes (it returned `Ok` before, which silently stopped the bridge while the process stayed alive). All shared `std::sync::Mutex` locks use `.lock().unwrap_or_else(|e| e.into_inner())`, so one panic while holding a lock cannot cascade into a permanent routing outage.
    Why it matters: "always-on and never crash" is priority one, and the old `tokio::join!` plus the bridge `Ok` path let a whole transport die invisibly. Also from the same audit: Biome now lints `skills/**/*.js` with an override that turns off `noUnusedVariables` and `noApproximativeNumericConstant`, because a profile's `const taste` is injected into the eval context (intentionally unused in-file) and ratios like `1.414` are deliberate design data, not a misspelled `Math.SQRT2`.

23. **Two Figma plugin-load constraints, both load-bearing (2026-08-06, Phase 9 live test).** First, the Figma main-thread runtime rejects ES module syntax: a bundle with a top-level `export`/`import` fails to load. Both plugin bundles must be classic scripts, so `code.ts` builds with `--format=iife` and the UI `main.ts` builds as an IIFE via `build-ui.ts`. Second, `networkAccess.allowedDomains` rejects a wildcard port (`ws://localhost:*` is "not a valid URL"); Figma allows wildcards only for subdomains. To let the plugin follow a user-configurable `TURBOFIG_WS_PORT`, `allowedDomains` is set to `["*"]` (allow-all), the only static value that covers any port. This is broader than ideal but acceptable for a local dev plugin talking to `127.0.0.1`; the alternative is a fixed port allowlist that drops arbitrary configurability. Extends #17: the plugin now has two build artifacts, `plugin/dist/code.js` and `plugin/dist/ui.html` (the manifest `ui` points at the built `dist/ui.html`). Third constraint (2026-08-07): `figma.fileKey` is a private-plugin API. It returns `undefined` unless the manifest sets `"enablePrivatePluginApi": true`, regardless of whether a file is open (`figma.root.name` is always available, but the key is gated). Without the flag the panel received an empty `fileKey`, so `updateFileDisplay` hid the whole fileKey row and both copy buttons. The flag is set and guarded by `plugin/src/manifest.test.ts`. This works for the dev-install model (#4); a Figma Community listing would disable private APIs, but Turbofig ships as a dev-install. Fourth and fifth constraints (2026-08-07, live UI test), both load-bearing, do not revert: the panel receives the Figma theme variables (`--figma-color-*`) only when `figma.showUI` is called with `themeColors: true`; without it the panel renders on its white fallbacks and ignores dark mode. And `navigator.clipboard` is unreliable inside the plugin iframe (it silently rejects), so both copy buttons use a hidden `<textarea>` + `document.execCommand("copy")`; reverting either reintroduces a bug the user hit live.

24. **Multi-file targeting is by `fileKey`, never by port (clarified 2026-08-06).** One daemon serves every open file on one port; each file's plugin opens its own WebSocket and announces its `fileKey`. A call routes to a file by an explicit `fileKey` argument, else the session-to-file pairing, else the sole connected plugin. So a single open file needs no targeting; several open files need a `fileKey` (or a one-time pairing) per Claude session. The plugin port field is therefore advanced config only. Phase 10 acts on this: hide the port field, surface a full copyable `fileKey`, and make the connection model self-evident. Refines the routing in #14/#15 with the user-facing model.

25. **Out-of-the-box usability: the daemon self-describes, ships a discoverability hook, and taste shapes colour by default (2026-08-06, Phase 10, driven by the first live Phase 9 test).** The live test surfaced three gaps: the AI did not know turbofig existed or how to drive it, the generated output ignored the taste profile and went all-purple, and the port field implied a wrong multi-file model (fixed by #24). Fixes: (a) the HTTP port is self-describing. A plain GET on `/` or any non-`/mcp` path returns a plain-text `HELP_TEXT` (the four tools, the file-bridge protocol, `fileKey` targeting, the ports), so an AI told only the port can bootstrap without the repo. (b) A shippable discoverability hook lives in `docs/discoverability/`: a `CLAUDE-snippet.md` a user pastes into a global CLAUDE.md and an `mcp-config.json` `mcpServers` entry for allowlisted native-MCP users. (c) Each taste profile gains a `palette` (`brand`, `accent`, `surface`, `surfaceAlt`, `text`, `textMuted`): a neutral-forward, non-purple, AA-passing default so `design.md` builds on the profile palette instead of inventing generic purple. `tf.taste` injection was already correct, so the all-purple cause was the workflow, not the daemon; `design.md` now prefers `tf.taste.palette` over a tone-derived palette when the brief gives no explicit hex. Extends #21 (profiles) and #24 (fileKey model).

26. **Discovery is file-bridge-first and web-fetch-safe (2026-08-07, live test).** A live paste of the connect prompt showed two failures: Claude Code turned "GET http://127.0.0.1:18846/" into a `WebFetch`, which force-upgrades to HTTPS and hit an SSL error on the plain-HTTP daemon; and the agent then wandered into an MCP `initialize` handshake instead of the file-bridge. So the connect prompt, the daemon `HELP_TEXT`, and `docs/discoverability/CLAUDE-snippet.md` now lead with the file-bridge (fastest, most token-efficient, no permission dialog: write `~/.turbofig/inbox/<id>.json`, read `outbox`, target by `fileKey`) and list MCP only as a labelled fallback, with an explicit "plain HTTP: use curl, never a web-fetch tool or HTTPS" warning. The connect prompt is kept to three dense lines so it does not bloat the agent context on first contact. Reinforces #15 and #20.

27. **Brand mark: motion ghost wordmark, CSS-only, theme-aware (2026-08-07, Phase 9 branding).** The turbofig brand mark is the word "turbofig" in a heavy condensed display face with a rightward ghost trail — 4 `text-shadow` layers at offsets 6/11/17/24px with opacity 44/22/10/4% — implemented as a single CSS rule using `color-mix(in srgb, var(--text) N%, transparent)`. No images, no JavaScript, no separate light/dark asset. The shadow colour derives from the live Figma theme token (`--figma-color-text`, injected via `themeColors: true`), so the effect adapts to Figma's light and dark mode automatically. The full Figma brand page is in the project file ("Brand" page) with exportable frames at 2× PNG: `wordmark-light`, `wordmark-dark`, `icon-light`, `icon-dark`. Export those manually to `docs/` before publishing the README or recording the demo.

28. **Product tagline: "bridge any AI to Figma" (corrected 2026-08-07).** The earlier tagline "always on Figma design agent" was wrong — turbofig is a bridge, not the agent itself. The daemon does not plan or design; it is the transport. The correct one-line positioning is "bridge any AI to Figma." Use this everywhere: README hero, About screen, connect prompt, any marketing copy. Do not revert to agent framing.
